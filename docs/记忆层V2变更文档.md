## 一、背景

### 变更前的问题

1. **记忆类型单一**：只有隐式的 4 种类型（summary / insight / topics / preference），无法区分"研究发现"和"行业实体"等不同性质的长期记忆
2. **更新方式粗暴**：每次压缩对话时，LLM 对整个摘要做全量覆盖，丢失未在当期对话中提及但仍有价值的历史细节
3. **检索粗放**：记忆全文直接注入 prompt，无分层加载机制，token 消耗高且难以控制
4. **记忆孤立**：条条记忆独立存储，之间无关联关系，无法形成研究知识图谱
5. **扩展困难**：新增记忆类型需要修改多处 Python 核心代码

### 变更目标

参考 OpenViking 记忆系统的设计理念，在现有 PostgreSQL + Milvus 基础上实现：

1. **YAML 配置化的记忆类型**：新增类型只需加一个 YAML 文件
2. **Patch 增量更新**：用 SEARCH/REPLACE 文本块只传输变更内容
3. **三层摘要体系**：L0 abstract（粗筛）→ L1 overview（注入 prompt）→ L2 detail（按需获取）
4. **记忆链接关系**：derived_from / related_to / contradicts，自动维护双向引用
5. **渐进增强**：不改动存储层和整体架构，仅升级记忆服务模块

### 3.3 `backend/app/schemas/memory_config.py`

**用途：** 定义记忆系统核心配置类型的 Pydantic Schema，供 YAML 解析和代码内类型声明使用。

```python
class MergeOp(str, Enum):
    """字段合并策略枚举"""
    PATCH = "patch"          # SEARCH/REPLACE 文本增量替换
    REPLACE = "replace"      # 全量覆盖
    SUM = "sum"              # 追加到末尾
    IMMUTABLE = "immutable"  # 创建后不可修改

class FieldType(str, Enum):
    """字段类型枚举（当前仅支持 string，预留扩展）"""
    STRING = "string"

class MemoryField(BaseModel):
    """单个字段定义"""
    name: str                                         # 字段名
    type: FieldType = FieldType.STRING                # 字段类型
    description: str = ""                             # 字段描述（会注入 LLM prompt）
    merge_op: MergeOp = MergeOp.PATCH                 # 合并策略

class MemoryTypeSchema(BaseModel):
    """记忆类型完整定义"""
    memory_type: str                                  # 类型名称（如 research_finding）
    description: str = ""                             # 类型描述（会注入 LLM prompt）
    directory: str = ""                               # 文件目录模板（预留）
    filename_template: str = ""                       # 文件名模板（预留）
    embedding_template: str = ""                      # 向量化文本模板
    fields: list[MemoryField] = Field(default_factory=list)  # 字段列表
```

### 3.4 `backend/app/config/memory_types/research_finding.yaml`

**用途：** 定义"研究发现"记忆类型的 schema

```yaml
memory_type: research_finding
description: |
  研究发现与结论 - 跨会话可复用的研究成果。
  提取研究过程中形成的事实结论、数据分析结果、趋势判断。
directory: "user/{user_id}/memories/findings"
filename_template: "{topic}.md"
embedding_template: "研究主题: {topic}\n结论: {conclusion}"

fields:
  - name: topic
    type: string
    description: 研究主题，作为唯一标识
    merge_op: immutable      # ← 不可修改，用于查重匹配
  - name: conclusion
    type: string
    description: 核心结论，支持增量补充
    merge_op: patch          # ← 增量更新，只修改变化的文本
  - name: confidence
    type: string
    description: 结论置信度（高/中/低/推测）
    merge_op: replace        # ← 直接覆盖
  - name: sources
    type: string
    description: 信息来源列表
    merge_op: sum            # ← 追加新来源
  - name: related_entities
    type: string
    description: 相关行业实体名称列表
    merge_op: sum            # ← 追加新实体
```

**关键设计点:**
- `topic` 设为 `immutable`，系统用此字段查重——同一主题的研究只保留一条记录，后续研究追加到同一条
- `conclusion` 设为 `patch`，LLM 只输出变更的文本块，不重写整个结论
- `sources` 和 `related_entities` 设为 `sum`，每次研究追加新来源

### 3.6 `backend/app/service/memory_merge.py`

**用途：** 实现四种字段合并策略的核心逻辑

```python
def apply_merge(current_value: str | None, patch_value: str, merge_op: MergeOp) -> str
```

**四种策略的处理逻辑：**

| 策略 | current_value 有值 | current_value 为 None |
|------|-------------------|----------------------|
| `REPLACE` | 返回 patch_value | 返回 patch_value |
| `IMMUTABLE` | 返回 current_value（忽略 patch） | 返回 patch_value（首次写入） |
| `SUM` | `current_value + "\n" + patch_value` | 返回 patch_value |
| `PATCH` | 解析 SEARCH/REPLACE 块，逐块替换 | 返回 patch_value |

**PATCH 策略详细实现：**

1. LLM 输出格式: `"SEARCH: <旧文本>\nREPLACE: <新文本>"`
2. 多个块用 `---` 分隔，每个块独立处理
3. SEARCH 文本必须在 current_value 中存在，否则 REPLACE 内容追加到末尾
4. 非标准格式（无 SEARCH/REPLACE 标记）的块直接追加

**示例:**

```python
# LLM 输出: "SEARCH: 市占率约35%\nREPLACE: 市占率约42%"
# current_value: "新能源汽车市占率约35%，同比增长显著"
# 结果: "新能源汽车市占率约42%，同比增长显著"
```

### 3.8 `backend/app/service/memory_service.py`（核心重构）

此文件是本次变更最核心的部分，涉及 4 个方法的重大改写 + 8 个新增辅助方法。

#### 3.8.1 `summarize_conversation` 重写

**旧行为:**
- 返回 `{"summary": "对话摘要", "key_insights": [...], "user_preferences": {...}, "topics": [...]}`
- LLM prompt 是固定的 4 类输出格式

**新行为:**
- 返回 `{"preferences": {...}, "memories": [{...}], "topics": [...]}`
- LLM prompt 动态注入从 `MemoryTypeRegistry` 获取的记忆类型描述和字段信息
- 每条 memory 包含 `memory_type`、`action`（write/edit/delete）、`uri`、`page_id`、`fields`、`links`
- 兼容旧格式：返回结果始终包含三个 key

**新 prompt 结构:**
```
请分析以下对话，提取可跨会话复用的研究成果和行业实体信息。

对话内容：...
可用的记忆类型：        ← 动态注入
  research_finding: ...
    字段:
      - topic (immutable): ...
      - conclusion (patch): ...
  industry_entity: ...
    字段:
      - entity_name (immutable): ...
      ...

操作说明：              ← 新增
- action=write/edit/delete
链接说明：              ← 新增
- link_type: derived_from / related_to / contradicts
字段合并策略：           ← 新增
- immutable / patch / replace / sum
```

#### 3.8.2 `create_memory` 重写

**旧行为:**
- 返回 `Optional[LongTermMemory]`（单条记忆）
- 直接将 summary_data 写入新记录，不做查重

**新行为:**
- 返回 `List[LongTermMemory]`（可创建多条结构化记忆）
- 完整流程：

```
1. 调用 summarize_conversation 获取结构化记忆列表
2. 遍历每条记忆：
   a. 检查 action: write → 查重后新建或合并, edit → 按 uri 查找后合并, delete → 删除
   b. 查重逻辑: 用 schema 中标记为 immutable 的字段（如 topic、entity_name）
      在 PostgreSQL 中做 JSONB 字段匹配
   c. 合并逻辑: 调用 _merge_fields() 按每个字段的 merge_op 合并新旧值
   d. 生成 L0 abstract（从 conclusion 截取首 100 字）
   e. 生成 L1 overview（从 fields 拼装概览文本）
   f. 记录 page_id → URI 映射
3. 链接后处理: 将 page_id 替换为真实 URI，写入 links/backlinks
4. Fallback: 无结构化记忆时，保存一条 traditional preference 记忆
5. 向量化: 对每条记忆生成 L0 abstract + L2 summary + topics 三个向量
```

#### 3.8.3 `build_memory_context` 重写

**旧行为:**
- 返回 `str`（拼接好的 prompt 文本）
- Milvus 搜索 top_k 条 → 拼接内容 → 返回文本

**新行为:**
- 返回 `dict`: `{"context_text": "...", "memory_ids": ["id1", ...]}`
- 三层分级检索：

```
Step 1 — 粗筛（向量搜索）
  Milvus 搜索 top-15，按 memory_type 分组（每种最多 3 条），去重

Step 2 — L1 注入（overview 级别）
  从 DB 查询 L1 overview，拼接到 context_text
  控制总 token 在当前 token 预算内（默认 800 tokens，约 2400 chars）

Step 3 — 按需展开（detail 级别）
  返回 memory_ids 列表，前端可调用 GET /memories/{id} 获取 L2 完整内容
```

**新增参数:**
- `max_memories`: 默认从 3 改为 5
- `max_tokens`: 新增，控制 context_text 最大 token 数（默认 800）

#### 3.8.4 `_store_memory_vectors` 重写

**旧行为:**
- 固定存储 3 类向量: summary / insight / topics
- 向量文本直接使用原始 summary 文本

**新行为:**
- 存储 L0 abstract / L2 summary / topics 三类向量
- summary 向量使用 schema 中定义的 `embedding_template` 渲染文本
- 新增 `memory_type` 参数，用于查找对应 schema
- 使用简单模板替换（`str.replace`）而非 Jinja2，减少依赖

#### 3.8.5 新增辅助方法（8 个）

| 方法 | 职责 |
|------|------|
| `_generate_abstract(text)` | 从长文本截取 L0 摘要（前 2-3 句） |
| `_generate_overview(type, fields)` | 从 fields 拼装 L1 概览文本 |
| `_merge_fields(existing, new, schema)` | 按 schema 的 merge_op 逐字段合并 |
| `_find_existing(db, user_id, type, fields, schema)` | 按 immutable 字段查已存在的记忆 |
| `_find_by_uri(db, user_id, uri)` | 按 UUID 查找记忆 |
| `_delete_by_uri(db, user_id, uri)` | 按 URI 删除记忆 |
| `_merge_links(existing, new, page_id_map)` | 合并链接列表，按序列化值去重 |
| `_update_backlinks(db, from_id, links)` | 更新目标记忆的反向链接字段 |

#### 3.8.6 `_db_query_by_id` 新增

用于 `build_memory_context` 中按 UUID 查 DB 获取 overview 字段。创建独立的短生命周期 DB session，在 finally 中关闭。

## 五、关键设计决策

### 5.1 为什么选择渐进增强而非完整重构？

- 现有 PostgreSQL + Milvus 存储层运转正常，不需要引入新的存储抽象
- 业务连续性：改动局限在 `memory_service.py` 内，`chat_service.py` 仅 1 行适配
- 风险可控：新旧逻辑可以在同一服务内共存，通过 `memory_type` 字段区分

### 5.2 为什么 LLM 提取记忆是"研究结束后的单次总结"而非"ReAct 循环提取"？

- 当前项目的深度研究流程本身已经是 ReAct 模式（PLAN → RESEARCH → ANALYZE → WRITE → REVIEW）
- 在 ReAct 内再嵌套一个 ReAct 会导致调用链路过长、延迟过高
- 研究结束后的单次总结对记忆提取任务来说是足够的——研究过程中 Agent 已经做了充分的探索和反思

### 5.3 为什么 patch 实现是字符串级 SEARCH/REPLACE 而非结构化 diff？

- 简化 LLM 输出格式：只需要 "SEARCH: <旧文本>\nREPLACE: <新文本>"
- 与 OpenViking 的 StrPatch 设计一致，易于后续升级
- 不需要额外的 diff 计算库

### 5.4 为什么 embedding_template 用 str.replace 而非 Jinja2？

- 减少依赖：不需要引入 Jinja2
- 模板变量简单（仅 `{topic}`, `{conclusion}` 等），str.replace 足够
- 后续可升级为 `str.format_map` 或 Jinja2

## 八、后续扩展
